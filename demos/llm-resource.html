What This Is

The core insight: Stop treating LLMs like magic boxes. Treat them like senior team members — they need clear context, explicit boundaries, and feedback loops before they can do their best work. Most people skip that setup and then blame the model when output is inconsistent.

This page documents the mental models, system prompts, and workflow patterns I've developed working directly inside Claude Code — Anthropic's agentic CLI environment. That's the primary focus, because it's where I've gotten the most reliable, production-quality results. The core logic transfers to other LLMs (GPT-4, Gemini, etc.) even if the specific commands differ.

Everything below is drawn from real projects: the patterns that held up, the shortcuts worth memorizing, and the self-correction loops that reduce how often you need to intervene. Not theory — accumulated experience.

Setting Up Claude Code the Right Way

Most people install Claude Code and start typing. It produces results — but each session starts cold. Claude doesn't know your environment, your rules, what you tried last week, or why a particular approach was abandoned. You end up re-explaining the same context, watching it suggest things you already ruled out, and manually catching regressions that a better setup would have prevented.

The six patterns below fix that. They shift Claude from a one-session tool into a compounding system — one where every decision you document, every rule you write, and every workflow you define makes the next project faster and more reliable than the last. The context you build in project A carries forward into project B. Global skills you write once are available everywhere. Memory files mean you never explain the same thing twice.

During conversations, the habits that matter most: write decisions to memory the moment they're made (not at session end — sessions close unexpectedly), use /compact before switching sub-tasks to keep Claude oriented, and if Claude suggests something you've already solved — stop, don't correct it manually, update the memory so it never happens again. Corrections that stay in chat die with the session. Corrections that go into memory become permanent rules.

The goal isn't a perfect first session. It's building infrastructure so every session after that is better than the one before.

Global CLAUDE.md: Your Persistent Rules Engine

SETUP

~/.claude/CLAUDE.md (Windows: %APPDATA%\Claude\CLAUDE.md) applies to every project, every session. Claude reads it before anything else. Put in it: your OS and shell, universal "never do X" rules, where API keys live, tool preferences. One rule written here follows you across every project forever — no re-explaining.

📄 What to put in ~/.claude/CLAUDE.md
# ~/.claude/CLAUDE.md ## Environment - Platform: Windows 11, PowerShell. Use $env:VAR not $VAR. - Python: conda env py311. Always activate before scripts. - Node: use npx.cmd (not npx) in subprocess calls on Windows. ## Universal Rules - Never push to git without explicit user approval. - Always read project CLAUDE.md before touching any file. - Check memory/ directory before suggesting anything new. - API keys live in D:\Apps\.env — never ask for them in chat.

Project CLAUDE.md: Scoped Context That Stacks

SETUP

Each project gets its own CLAUDE.md in the root. It stacks on top of global — project rules win where they conflict. Document: what the project is (one paragraph), the active workflow (exact commands: how to preview, how to deploy), hard constraints ("never edit X file"), and file locations that aren't obvious from the directory structure. If future-you would have to guess — write it down now.

📄 What to put in your project's CLAUDE.md
# myproject/CLAUDE.md ## What This Is A static portfolio site. No src/ — only compiled dist/ output. Cannot run `npm run dev`. Original source lives elsewhere. ## Workflow 1. Edit files locally. 2. Preview: python preview.py → http://localhost:8001 (F5 to refresh) 3. Push ONLY when user says so: python push.py "commit message" ## Never - Run git push directly — use push.py (avoids CRLF phantom diffs) - Edit assets/index-*.js — it's a compiled bundle, machine code - Push without explicit user confirmation every single time

Memory Files: Notes That Survive Sessions

MEMORY

Claude has zero memory between sessions by default. Fix this with a memory/ directory — per-project or global. MEMORY.md is the index (always loaded, one line per file). Each file covers one topic. Claude reads them at session start and updates them mid-session. Four types worth having: user (who you are, how you work), feedback (corrections + validated wins), project (current goals, decisions, deadlines), reference (where things live externally). Write it once, never explain it again.

📁 How your memory/ folder should look
memory/ ├── MEMORY.md ← index (always loaded, ~150 char lines) ├── user_profile.md ← role, preferences, communication style ├── feedback_rules.md ← corrections + confirmed working patterns ├── project_state.md ← current phase, decisions, deadlines └── reference_links.md ← Grafana URL, Linear project, Slack channel # Inside MEMORY.md (the index): - [User Profile](user_profile.md) — builder, output-focused, terse - [Feedback Rules](feedback_rules.md) — never mock DB, use push.py - [Project State](project_state.md) — phase 1 complete, phase 2 TBD

Skills & Agents: Utilities That Work Across Every Project

ADVANCED

Skills are markdown files in ~/.claude/skills/ that define how Claude handles specific task types. Once written, invoke from any project with /skill-name. Think of them as your personal playbooks — video production workflow, UI testing patterns, API design conventions. Agents extend this further: spawn sub-agents for parallel research or isolated tasks, protecting your main context window from getting polluted by large code dumps. The more skills you write, the faster every new project starts.

⌨️ How to invoke skills & spawn agents
# Invoke a global skill from any project: /webapp-testing ← Playwright UI test patterns /story-director ← director's brief for video pipelines /vercel-react ← React/Next.js performance patterns # Spawn a focused sub-agent (Claude Code): Agent({ subagent_type: "Explore", prompt: "Find all API endpoints" }) → Runs isolated, returns result, main context stays clean # Build a new skill when you find yourself explaining # the same workflow in 3 different projects.

Conversation Management: Avoiding Drift & Circles

WORKFLOW

Long conversations degrade. The context window fills with noise, prior decisions get buried, Claude starts contradicting itself and suggesting things you already solved. The fix is three habits used together: /compact before starting a new sub-task (compresses history, keeps orientation), /cost before any large operation (know where you stand), and writing decisions to memory immediately — not at end of session, because sessions end unexpectedly. If Claude suggests something that was already figured out two weeks ago, that's a memory gap, not a model failure.

⚡ Commands to run & habits to avoid
/compact ← compress conversation history, keep working /cost ← check token usage before a big task /clear ← full reset (context gone — use carefully) # Anti-patterns that cause circular sessions: ✗ Letting conversation grow to 50+ turns before compacting ✗ Assuming Claude remembers a decision from 30 msgs ago ✗ Explaining the same project context twice in one session ✗ Not writing a decision to memory before closing the tab # After any major decision, say immediately: "Save this to memory: [the decision and why]"

Anti-Regression: Make Sure You Never Move Backwards

WORKFLOW

The most expensive failure mode: Claude solves a hard problem, the session ends, next session it recommends the same broken approach that was already ruled out. Prevention is a system, not a habit. The feedback memory type exists for exactly this — but only works if you capture the why, not just the what. "Don't mock the DB" is useless without "prior incident — mock passed, prod migration failed silently, 3 hours to diagnose." The why is what lets future Claude judge edge cases instead of blindly applying the rule. Also: before implementing anything, Claude should check memory for prior attempts on the same problem — if something similar failed before, surface it.

📝 How to write a feedback rule that actually sticks
# memory/feedback_rules.md ## Integration tests must hit a real DB — never use mocks. **Why:** Prior incident — mocked tests passed but prod migration failed silently. Took 3 hours to diagnose the divergence. **Apply:** Any test that touches the database layer. ## Always check memory before suggesting new tooling. **Why:** Existing pipeline scripts already handle transcription, AI planning, and video editing. Suggesting alternatives wastes time. **Apply:** Any task involving video, audio, or AI orchestration. ## Never git push directly — always use push.py. **Why:** CRLF line-ending flip causes phantom diffs across entire repo at session start. push.py uses Git Data API (file-list only). **Apply:** Every single deploy, no exceptions.

Claude Code Built-in Command

/goal — Autonomous Task Completion

Set a verifiable end condition once. Claude works until it's met — no re-prompting required.

/goal [condition]
What it actually does

Most Claude interactions are reactive — you prompt, Claude responds, you decide what's next. /goal flips this. You define an end state, and Claude drives itself toward it across as many turns as it takes — automatically, without you typing another message.

The key mechanism: a separate evaluator model (not Claude itself) checks the condition after every turn. If the condition isn't met, the evaluator explains why — and Claude starts the next turn automatically. This separation matters: the model doing the work doesn't decide when to stop. An independent judge does.

How the loop runs
1

You type /goal [your condition]

One time. That's it. The condition is your measurable end state — what "done" looks like.

2

Claude works — Turn 1

Claude reads your goal and starts executing toward it. Edits files, runs commands, reads output — whatever is needed.

3

Evaluator checks the condition

A separate model reads the conversation transcript. It doesn't run commands — it judges based on what Claude surfaced (test output, git status, etc.).

4a

Not met → Next turn starts automatically

Evaluator explains what's missing. Claude starts the next turn without waiting for you. You don't type anything.

4b

Met → Goal clears, control returns to you

Goal is recorded as achieved. The loop ends. You get the session back.

Concrete example — fixing a failing test suite
❌ Without /goal (reactive)
You: migrate payment module
Claude: [edits 2 files]
You: run the tests
Claude: [3 tests fail]
You: fix the failing tests
Claude: [fixes them]
You: check if anything else broke
Claude: [full suite passes]
→ You typed 4 prompts
✅ With /goal (autonomous)
You: /goal all tests in test/payment
      pass and lint is clean
Turn 1: migrates API calls
Eval: No — 3 tests failing
Turn 2: fixes failing tests
Eval: No — lint has 2 warnings
Turn 3: fixes lint warnings
Eval: ✓ Condition met
→ You typed 1 prompt
Writing conditions that work

The evaluator only reads the transcript — it can't run commands or check your actual system. Your condition must be something Claude can surface in its output so the evaluator can verify it.

✅ Good conditions
"all tests in test/auth pass
and lint step is clean"
"git status is clean and
CHANGELOG has a new entry"
"preview loads with no JS errors
in the browser console"
❌ Bad conditions
"make it look better"
— subjective, not verifiable
"fix the database schema"
— evaluator can't check the DB
"everything works"
— too vague to evaluate
Pro tip: Add a turn cap to prevent infinite loops: /goal all tests pass — or stop after 15 turns
/goal vs. alternatives
Approach Next turn triggers when Stops when Best for
Plain text You type a new message You stop typing Exploratory, back-and-forth work
/goal Previous turn finishes Evaluator confirms condition met Defined end states — tests, deploys, file states
/loop Time interval elapses You stop it manually Polling, monitoring, recurring tasks
Stop hook Previous turn finishes Your script decides Permanent per-session automation (settings.json)
What /goal persists
The condition
Survives session resume with --resume or --continue
Progress stats
Turn count, elapsed time, and token spend tracked across turns
Evaluator reasoning
Why each turn didn't satisfy — visible in the transcript after each check
Auto-clears on success
Goal clears itself when met. Manual clear: /goal clear
